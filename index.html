This documentation covers the design, implementation, and evaluation of a Storage Area Network (SAN) built entirely from consumer-grade hardware. My goal was to prove that the behavior of enterprise storage—specifically block-level access and VLAN isolation—could be replicated in a home lab environment.

00. Context & Objective

During the initial project definition, my mentors advised that a standard NAS (Network Attached Storage) project would not be sufficiently challenging for Semester 6 standards. [cite_start]A NAS operates at the file level (SMB/NFS), introducing overhead and latency that makes it unsuitable for heavy virtualization workloads [cite: 68-69].

[cite_start]The Challenge: "How can I design, implement, and validate a functional SAN using only consumer-grade hardware, while proving its superiority over NAS in performance and use-case suitability?"[cite: 74].

02. Getting a Clean Start

I started by repurposing my Intel NUC. It was previously a home lab server, but for this research, I needed a clean slate to document every step.

    [cite_start]
  • Boot Media: Created a bootable USB with Rufus using the Ubuntu Server 24.04.3 LTS ISO [cite: 191-192].
  • Installation: Wiped the internal NVMe drive and performed a fresh install.
    • [cite_start]
  • Networking: Configured a static IP 192.168.2.200 during installation via Netplan to ensure the Target is always reachable[cite: 194].

03. Storage Backend Configuration

Connecting the 1TB external HDD was the first physical step. I ran lsblk and found an old NTFS partition on /dev/sda. I decided to wipe it completely for native Linux performance.

BASH 
# 1. Wipe the disk and format to ext4
sudo mkfs.ext4 -F /dev/sda

# 2. Create the mount point
sudo mkdir /san
sudo mount /dev/sda /san

# 3. Persist via fstab (using UUID for safety)
# Extracted UUID via 'sudo blkid /dev/sda'
echo "UUID=2e3581a1-60e0... /san ext4 defaults 0 2" | sudo tee -a /etc/fstab

[cite_start]After mounting, I confirmed I had 916GB of available space ready for the SAN[cite: 204].

04. Installing iSCSI Target (LIO)

I chose targetcli-fb as it is the standard administration shell for the Linux-IO (LIO) subsystem.

TERMINAL 
sudo apt install targetcli-fb -y
sudo systemctl enable --now target

# Create the config directory manually (quirk of the package)
sudo mkdir -p /etc/target

Creating the LUN (Logical Unit Number)

Instead of passing the whole physical disk, I created a 100GB file-backed image. This allows the SAN to be flexible—I can grow it later or have multiple LUNs on one physical disk. 

# Create the 100GB Backstore
/backstores/fileio create name=lun0 file_or_dev=/san/lun0.img size=100G

# Create the Target Identity (IQN)
/iscsi create iqn.2025-11.nl.fontys:san

# Map the LUN to the Target
/iscsi/iqn.2025-11.nl.fontys:san/tpg1/luns create /backstores/fileio/lun0

05. The CHAP Security "Drama"

This was the most challenging part of the implementation. Security is mandatory for enterprise environments, so I attempted to enable Mutual CHAP (where both the client and server authenticate each other).

The Struggle: Windows 11 refused to connect with Mutual CHAP enabled. [cite_start]After researching, I found this is a known limitation in the Microsoft Initiator[cite: 268]. Furthermore, I initially used a 21-character password which caused handshake failures.

The Final Working Configuration:

  • Mode: Unidirectional CHAP (Client authenticates to Target).
  • User: kevin
  • Password: KevinPass123 (Exactly 12 characters to be safe).
TARGETCLI CONFIG 
# 1. Create ACL for the laptop
/iscsi/.../tpg1/acls create iqn.1991-05.com.microsoft:kevin-s-lap

# 2. Set Authentication (Unidirectional only)
cd /iscsi/.../tpg1/acls/iqn.1991-05.com.microsoft:kevin-s-lap
set auth userid=kevin password=KevinPass123
set auth mutual_userid= disabled

06. Client Integration (Windows)

With CHAP fixed, I moved to the Windows laptop (University Laptop). I used the Microsoft iSCSI Initiator GUI because the command line `iscsicli` tool was giving me legacy authentication errors.

  1. Discovery Portal: Added 192.168.2.200.
  2. Connect: Selected the Target -> Advanced -> Enable CHAP Log on.
  3. Disk Management: The 100GB LUN appeared as "Disk 1". [cite_start]I initialized it as GPT and formatted it as NTFS [cite: 251-257].

I verified the write access with a simple CLI test: echo SAN WORKS! > S:\proof.txt

07. Network Isolation (VLANs)

To mimic enterprise security, I replaced my dumb switch with a Netgear GS105E Managed Switch. I configured 802.1Q VLANs to "air-gap" the storage traffic from the home internet.

  • VLAN 1 (Home): Ports 1 & 5 (Router Uplink).
  • VLAN 10 (SAN): Ports 2, 3, 4 (NUC & Laptops).

Result: When connected to Port 2, I can see the SAN. When on Wi-Fi, the SAN IP 192.168.2.200 is completely unreachable. [cite_start]This prevents unauthorized scanning of the storage network [cite: 325-330].

08. Performance Benchmarks

I ran CrystalDiskMark 9.0.1 to compare the iSCSI SAN against a temporary SMB (NAS) share I set up on the same NUC.

Metric iSCSI SAN (Block) NAS (File) Verdict
Seq. Read 117.41 MB/s 117.52 MB/s Tie (Network Limited)
Random Read 4K 101.51 MB/s 11.25 MB/s SAN Wins (9x Faster)
Random Write 4K 0.16 MB/s 9.05 MB/s HDD Bottleneck

[cite_start]Analysis: The Sequential Write (9.23 MB/s) was low due to the USB 3.0 HDD translation layer bottleneck[cite: 379]. [cite_start]However, the Random Read performance proves the hypothesis: Block-level storage is vastly superior for latency-sensitive workloads like VM booting or databases[cite: 291].
